# RAPP OS

**A static operating system.** Its global filesystem is a public GitHub Pages tree —
read-only, addressed by real URLs, identical on every device on earth. Its writable
filesystem lives only on the machine you are sitting at, and never leaves it.

**Boot it:** https://kody-w.github.io/OS/console/

No install, no account, no server. Open the URL on a phone in a queue and you get the
same system32 as a laptop in another hemisphere.

---

## Two layers

|  | **DOG** | **GOD** |
|---|---|---|
| | Distributed Object Graph | Grounded Object Device |
| Scope | every device on earth | this browser profile, this machine |
| Mode | read-only | read-write |
| Backing | GitHub Pages + raw.githubusercontent.com | IndexedDB |
| Addressing | real URLs — `curl` it from your shell | a key in a local store |
| Durability | as durable as a public git repo, with a diff per change | until you clear site data |
| Who can read it | anyone, forever | you |

The union resolves **GOD before DOG, first hit wins.** So editing a global file writes a
local copy that shadows it. The global file is never touched, because it *cannot* be:
your browser has no write path to somebody else's Pages site.

That constraint is the design, not a limitation. A globally writable layer needs accounts,
auth, quotas, moderation and a server. Making the global layer read-only is exactly what
lets the entire OS be static files. Writes are a local concern, so they go to a local
device.

### Deleting what you don't own

You cannot delete from DOG, and pretending otherwise would be a lie. `rm` on a global path
writes a **whiteout** — a tombstone in GOD. The union then reports the path as absent *on
this device only*. Everyone else still sees the file. `unrm` and it returns.

```
$ stat /OS/system32/etc/motd
  layer  DOG    global, read-only, same for everyone
$ cp /OS/system32/etc/motd /OS/system32/etc/motd
  copied (DOG) -> (GOD, 764 B)
$ stat /OS/system32/etc/motd
  layer  GOD    this device only, writable
$ rm /OS/system32/etc/motd        # removes your copy
$ stat /OS/system32/etc/motd
  layer  DOG    ...the global file was never touched
$ rm /OS/system32/etc/motd        # now there is nothing of yours left to remove
  whiteout — hides it on this device. Everyone else still sees it.
```

## It really boots

Not an animation. Every line is a measurement of the machine you are on:

```
[BIOS ] boot device  /OS/boot/boot.json 3ms
[POST ] storage..... OK  IndexedDB, 983 B used of 6.49 GB 12ms
[POST ] network..... OK  fetch, HTTPS to kody-w.github.io
[POST ] crypto...... OK  SubtleCrypto
[POST ] workers..... OK  16 logical cores
[POST ] display..... OK  1200x900 @ 1x
[KRNL ] rapp-kernel 1.0
[KRNL ] vfs union GOD -> DOG  first hit wins
[MOUNT] DOG ro  https://kody-w.github.io  1222 nodes, 32 dirs 3ms
[MOUNT] GOD rw  idb://rapp-os/god  device e58df321dd7d  0 files
[INIT ] init 5 services
RAPP OS 1.0 "Doghouse"  boot complete in 726ms
```

A failed POST that matters halts the machine. `dmesg` replays the log with timings.

The hostname is derived from a SHA-256 over this device's user agent, language, screen
size, timezone offset and core count — stable for this machine, and it never leaves it.

## The static API

There is no API server. **The API is files**, so anything that speaks HTTP can drive the
OS: this shell, your terminal, a script, another agent, in ten years.

| Endpoint | What |
|---|---|
| [`/OS/boot/boot.json`](https://kody-w.github.io/OS/boot/boot.json) | the boot record: POST checks, mounts, devices |
| [`/OS/system32/kernel.json`](https://kody-w.github.io/OS/system32/kernel.json) | the VFS contract |
| [`/OS/system32/init.json`](https://kody-w.github.io/OS/system32/init.json) | services started at boot |
| [`/OS/api/dogfs.json`](https://kody-w.github.io/OS/api/dogfs.json) | the DOG index, regenerated by Jekyll on every build |
| [`/OS/api/version.json`](https://kody-w.github.io/OS/api/version.json) | identity |
| [`/api/examples.json`](https://kody-w.github.io/api/examples.json) | the site's own API, mounted as a character device |

`fs.json` is generated from the real site tree, so the filesystem is never a hand-kept
copy of itself: publish a post, and it appears in the OS.

```bash
curl -s https://kody-w.github.io/OS/system32/etc/motd
curl -s https://kody-w.github.io/OS/api/dogfs.json | jq '.nodes | length'
```

**The index is a listing; the wire is the authority.** If a path is served but missing from
`fs.json`, the OS reads it anyway and tells you it was unindexed. On DOG, existence is
whatever the origin says it is.

## Shell

```
ls cd pwd cat stat tree find          look around, either layer
echo > write cp rm unrm               write — always lands in GOD
mount df uname whoami hostname id     what this machine is
dmesg ps uptime date fsck             what it is doing
curl open                             reach the DOG directly
export import wipe reboot clear       your data is yours
```

`stat` answers the only question that matters in a union filesystem: **which layer did
this actually come from?** `export` hands you the entire GOD layer as JSON — nothing was
ever uploaded, so this is the only copy. `import` puts it on another device.

## The other front end

[`/OS/`](https://kody-w.github.io/OS/) is a desktop over the same public volume: a dock,
windows, and a curated mount tree in `api/fs.json`. It is deliberately read-only and
stores nothing.

This console is the other half — same DOG, plus a writable GOD layer, a real boot and a
shell. They share `/OS/system32/`: the desktop renders it as a page, the console reads
the same directory as files.
